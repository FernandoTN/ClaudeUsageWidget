The model: two words, three pointers

freeViewing

The one account the inspector, the popover's name menu and single-account bar mode show and operate on. Picking a name anywhere (inspector row, popover menu, the ⌘-hotkey) only views. Never touches a CLI, never records a switch, never starts a fetch, never changes a timer, never needs the dead-login gate. (Storage: today's activeProfileId, unchanged.) A tile click or the ‹ › navigator is a lighter, unsaved "look" and stays that way.

costly · deliberateActive for Claude · Active for Codex · Active for Grok

The three accounts the CLIs actually use. Changed only by "Make active for <provider>…" (always with a confirmation that states the cost and the candidate's evidence), by the auto-switch, by a login you made on the CLI side that the sweep adopts (reported once: "Active for Claude changed outside the app: now Lark"), or by an explicit Import of the CLI's current login into a profile (named and confirmed — that is a switching action too). The cyan tile label keeps meaning exactly this.

Rule everywhere: when the account you are viewing is not the provider's active one, both facts are shown side by side — Viewing Cedar · Active for Claude: Atlas. The word "Active" without a provider is never displayed again. Focus is never authority: no sweep, gate, probe or trigger reads the viewed profile to decide anything about a CLI. Every number carries provenance + age ("own · 28 s ago", "headers · 3 m ago"), and every login verdict its kind ("probed 12 m ago"), so a blind account reads as blind.

Decision 2 — selector on by default; confirmation on every manual switch

RECOMMENDED

On by default · confirm every manual switch, never suppressible

It is what you asked for and it is additive (one toggle in Display hides it). Every manual switch shows the cost sentence and the candidate's evidence; there is no "don't ask again" — your ruling is that a switch is deliberate, and two of the three reviews said a suppression box contradicts it. Auto-switches never confirm (they already meet the thresholds and the queue you set).

Alternatives

Off by default — you enable it once. Suppressible per provider — a "don't ask again for Claude" box (forced anyway for unverified / dead / duplicate candidates). Never confirm — the menu row's text carries the cost, one click switches (fastest, least deliberate).

Decision 4 — the one habit change: the popover's name menu and the ⌘-hotkey become view-only

Today picking a name in the popover menu (and the "next profile" hotkey) switches the CLI. Decision 5 — Codex usage limit resets (your ask tonight)

Facts verified from the codex CLI source and read-only probes on all five local Codex homes (docs/research/2026-09-03-codex-bank-resets-*.md): the official name is "usage limit resets" (the CLI's /usage → Redeem usage limit reset); the count is already in the usage payload the widget fetches (but it is null when you have none — indistinguishable from zero, so we show "none / unknown", never "0"); expiry comes from a detail endpoint that rate-limits hard, so it is fetched only when you open an account or press Details; redeeming is a POST with an idempotent id and four result codes. Credits look like grants ("earned reset"), not a monthly allotment — no schedule or refill date is ever implied. All five accounts hold zero right now, so "use one" ships source-verified and gets its first live test when an account earns a credit.

RECOMMENDED

Show count + expiry everywhere the account appears; "Use a usage limit reset…" only when the account is measured at its limit

Shown on the Codex active card, the ⇄ Codex section, the inspector Overview ("Usage limit resets: 2 available · next expires Sep 9 · Details") and as a roster badge. The action is enabled only when the account is measured at its limit (weekly ≥ threshold or a server-affirmed stamp — never on suspicion, never with headroom: a reset is never spent for nothing), confirms with "Use one usage limit reset for <account> (same as the CLI's Redeem)", is strictly manual, and shows the outcome in place ("Reset applied · 2 windows cleared"). Hidden for API-key Codex profiles (they have none).

As recommendedShow count only, no in-app redeemAllow redeem at any time (with confirmation)

Dashboard depth (stage 4) — pick the order

B2 already shows: active card with gauges + thresholds + provenance + suspected caveat + ETA, next candidate with verdict age, the queue slice, two-line roster rows with chips and repair links, account detail, "Make active…" two-step, five recent switches. Stage 4 adds, all additive, in this proposed order:

  1. Reset timeline — the next 7 days with a marker per account at its weekly / Fable reset and the headroom that returns (when does capacity come back). All three reviews: ship this first.
  2. Blind spots — per active account: seconds since the last own measurement, provenance of the shown number, header-rescue count per hour, backoff state (tonight's 3-minute blind window, 19:35–19:38).
  3. Drift banner — the CLI's live identity differs from the recorded owner, or an owner changed outside the app.
  4. Switch log — the full 30-entry ring with provider filter, trigger and reason.
  5. Burn rate — pp/min with the last samples as a sparkline; why an account is projected to cross, not just when.
  6. Rate-limit incidents — transcript tripwire events, stamps, probe 429s, per account, last 24 h.
  7. Roster filters — readiness, provenance, stale > N min, queued only, provider.
  8. Capacity remaining — Σ of unused weekly quota over live distinct accounts, per provider.
  9. "Why not the others" — each blocked candidate's evidence and age in one place before a manual switch.

Beyond this endeavour — the gaps the reviews found (pick what to pull in first)

  • Adding a Claude account without displacing the CLI login — every /login today replaces the shared login and the sweep adopts it. Claude Code honours CLAUDE_CONFIG_DIR; an isolated-config "Log in a new Claude account" flow, twin of the Codex one, is the largest gap in either spec. Recommended next.
  • Fetch budget at 30 Claude accounts — 2 background fetches per 30 s sweep means each account is measured every ~7 min and nearly every dot reads "stale". Cadence tiers (hot / warm / cold).
  • Per-provider auto-switch enable / thresholds — today one global toggle.
  • Bulk roster operations — multi-select → show on bar, eligibility, alerts, delete, label.
  • Archive state for lapsed subscriptions; backup / restore of the roster; notification digests; name-keyed history (renames break attribution); grouping by org.
